# 预测任务调度平台 · 半个月（15 个工作日）开发计划

> 本文是计划；每天实际完成了什么、怎么验证的，见 [DEVLOG.md](DEVLOG.md)（开发日志，每天随代码一起提交）。

## 1. 目标与范围

从零搭建一套**量价 / 负荷预测任务调度平台**，交付后具备以下能力：

| 能力 | 说明 |
|---|---|
| 对外预测接口 | 任务类型（LOAD / PRICE …）× 执行模式（预处理 / 训练 / 预测 / 一体化），异步提交 + 可选同步等待 |
| 流程编排 | 步骤可插拔、可配置编排，统一处理重试、取消、超时、轨迹记录 |
| Python 预测引擎 | FastAPI + pandas + scikit-learn，完成预处理、训练、预测；Java 通过 HTTP 协议调用 |
| 多表结构取数 | 长表、日期 + 时段、宽表三种布局统一映射为 `(series_key, ts, fields…)` |
| 预训练数据缓存 | 按时间分段的两级缓存（Caffeine + Redis），避免频繁读库 |
| 分批传输 | 分片 + gzip + CRC32 + 幂等上传 + 背压 |
| 定时调度 | 数据库配置的动态 Cron、集群去重、并发策略、错过补偿、失败重试 |
| 监控追踪 | 任务/步骤轨迹、链路追踪、Prometheus 指标、SSE 实时进度、回调通知 |
| 微服务化与交付 | Nacos 注册/配置、API 网关、声明式客户端、Docker Compose 一键部署 |

不在本期范围：前端页面、权限体系（仅 API Key）、模型效果调优（引擎为可替换的参考实现）。

## 6. 依赖关系与顺序说明

- **自底向上**：先定公共契约（D1 – D2），再做被依赖最多的持久化（D3），数据与引擎（D4 – D8）互不依赖、可并行，这里按“先 Java 取数、后 Python 引擎、再打通两者”的顺序串行安排。
- **D11 是关键节点**：之前每天交付的是可单测的部件，D11 把它们接成第一条端到端链路。D9、D10 任何延期都会直接推迟 D11。
- **调度与监控后置**：定时调度（D12）复用 D11 的提交入口，监控与回调（D13）通过监听任务事件接入，都不改动执行链路。
- **微服务化最后做**：网关、配置中心、客户端（D14）不影响核心功能，放在核心稳定之后。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Java 与 Python 的协议理解不一致 | D11 联调返工 | D6 用协议模型与测试把协议固定下来，D7 补齐协议文档；D11 的引擎替身严格按同一协议实现 |
| 大数据量传输占用内存 | 任务 OOM | D5 按分段流式读取、D10 按分片发送并用信号量限制在途分片 |
| 多实例重复触发定时任务 | 重复预测 | D12 用触发记录唯一键去重，再以幂等请求号做第二道保护 |
| 引擎抖动或长任务 | 任务失败、线程占用 | D8 重试 + 熔断；D10 异步提交 + 退避轮询；D9 步骤级重试兜底 |
| 进度滞后 | 交付延期 | D13 – D15 的内容可按优先级裁剪（接口文档、告警规则可后补），核心链路不受影响 |

## 8. 完成定义

每天的工作满足以下条件才算完成：

1. 代码已提交，`mvn verify` 通过（涉及 Python 的日子 `pytest` 通过）；
2. 当天新增的能力有对应的自动化测试，或在开发日志中记录了手工验证步骤与结果；
3. 开发日志已更新：完成内容、关键设计、验证结果、代码量、遗留问题。
